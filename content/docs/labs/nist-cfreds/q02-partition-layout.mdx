## Question

**Identify the partition information of the PC image.**

## Reusable concepts

This investigation applies:

- [Data Representation](/fundamentals/data-representation)
- [Offsets and Addressing](/fundamentals/offsets-addressing)
- [Volume Analysis](/filesystem-forensics/volume-analysis)
- [Master Boot Record (MBR)](/filesystem-forensics/volume-analysis/mbr)
- [NTFS Boot Sector](/filesystem-forensics/ntfs/boot-sector)

Question 1 is the integrity gate. Only after the image has been verified do we interpret its contents.

## Step 1 — Let fdisk describe the disk

~~~bash
fdisk -l cfreds_2015_data_leakage_pc.dd
~~~

Observed values:

~~~text
Disk size:       20 GiB
Total sectors:   41,943,040
Logical sector:  512 bytes
Disk label:      DOS / MBR
Disk identifier: 0xf0265720
~~~

| Partition | Boot | Start LBA | End LBA | Sectors | Approx. size | Type |
| --- | --- | ---: | ---: | ---: | ---: | --- |
| 1 | active | 2,048 | 206,847 | 204,800 | 100 MiB | 0x07 |
| 2 | — | 206,848 | 41,940,991 | 41,734,144 | 19.9 GiB | 0x07 |

At this point `fdisk` has interpreted the partition table. The next steps validate important values against raw bytes.

## Step 2 — Establish the MBR address space

For this image, `fdisk` reports 512-byte logical sectors.

~~~text
LBA 0
= bytes 0 through 511
= image offsets 0x000 through 0x1FF
~~~

~~~bash
xxd -g 1 -l 512 cfreds_2015_data_leakage_pc.dd
~~~

Observed MBR signature bytes at image offsets `0x1FE-0x1FF`:

~~~text
55 aa
~~~

The reusable structure is documented on the [MBR page](/filesystem-forensics/volume-analysis/mbr).

## Step 3 — Validate the disk identifier

At image offsets `0x1B8-0x1BB`:

~~~text
20 57 26 f0
~~~

Little-endian interpretation:

~~~text
0xf0265720
~~~

This agrees with `fdisk`.

## Step 4 — Decode partition 1

The first 16-byte partition entry begins at image offset `0x1BE`:

~~~text
80 20 21 00 07 df 13 0c 00 08 00 00 00 20 03 00
~~~

Relevant fields:

~~~text
80             boot / active flag
07             partition type
00 08 00 00    starting LBA
00 20 03 00    sector count
~~~

Decoded little-endian values:

~~~text
starting LBA = 2048
sector count = 204800
~~~

Image-absolute byte offset:

~~~text
2048 × 512
= 1,048,576
= 0x100000
~~~

Final LBA:

~~~text
2048 + 204800 - 1 = 206847
~~~

## Step 5 — Decode partition 2

The second partition entry begins at image offset `0x1CE`:

~~~text
00 df 14 0c 07 fe ff ff 00 28 03 00 00 d0 7c 02
~~~

Decoded values:

~~~text
starting LBA = 206848
sector count = 41734144
~~~

Image-absolute byte offset:

~~~text
206848 × 512
= 105,906,176
= 0x6500000
~~~

Final LBA:

~~~text
206848 + 41734144 - 1 = 41940991
~~~

## Step 6 — Validate the filesystem independently

Both partition entries use type `0x07`. That value is not sufficient by itself to prove NTFS.

~~~bash
fsstat -o 206848 cfreds_2015_data_leakage_pc.dd
~~~

Filesystem-level output is coherent with NTFS and includes:

~~~text
Sector size:  512 bytes
Cluster size: 4096 bytes
~~~

## Answer

~~~text
Partition 1
  Start LBA:     2048
  End LBA:       206847
  Sector count:  204800
  Byte offset:   0x100000
  Size:          100 MiB
  Active:        yes

Partition 2
  Start LBA:     206848
  End LBA:       41940991
  Sector count:  41734144
  Byte offset:   0x6500000
  Size:          approximately 19.9 GiB
~~~

Filesystem-level validation confirms NTFS for the later analysis.

## What this establishes

~~~text
verified image
  ↓
fdisk reports 512-byte logical sectors
  ↓
inspect image bytes 0x000-0x1FF
  ↓
decode raw partition entries
  ↓
LBA × 512
  ↓
image-absolute partition offsets
  ↓
fsstat provides independent filesystem-level validation
~~~

## What this does not establish

The partition table does not identify the installed Windows version, user activity, accounts, or the meaning of later filesystem artifacts.
